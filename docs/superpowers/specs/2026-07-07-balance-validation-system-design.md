# Tiny Cosmos 平衡验证系统设计归档

状态：已完成
设计日期：2026-07-07

## 目的

平衡验证系统为资源循环建立可重复的比较方法，主要回答：

- 玩家能否按合理节奏解锁各层。
- 生产、代谢、研究和大坍缩是否保持一致。
- 新机制是否改变决策并保留基础进度。
- 是否出现停滞、失控增长或界面数值错误。

## 项目结构

项目使用原生 HTML、CSS 和 JavaScript：

- `js/constants.js`：层级、成本、产量、研究、大坍缩和里程碑数值。
- `js/state.js`：可保存状态和状态操作。
- `js/engine.js`：生产、代谢、研究、合成和大坍缩逻辑。
- `js/ui.js`：界面卡片和操作。
- `js/render.js`：画布表现。

验证工具在 Node 中加载常量、状态和引擎，不加载界面与画布。

## 第一阶段目标

第一轮大坍缩需要通过固定策略抵达，同时保留 10、30、60 分钟检查点。

参考进度：

- 0—10 分钟：理解点击、生产者、合成和研究。
- 10—30 分钟：自动生产开始承担主要增长，接近原子和分子。
- 30—60 分钟：进入中段资源链，避免长时间停滞。
- 第一轮大坍缩：文明和坍缩入口可抵达。
- 第二轮开局：恒定点产生清楚且受控的提速。

## 验证场景

### `idle-10m`

十分钟内不执行手动操作，用于检查被动生产、研究和开局提示。

### `click-start-10m`

开局进行有限点击，随后按固定规则购买生产者、研究和合成。

### `guided-30m`

运行三十分钟固定策略：优先购买有用生产者、合成当前最高可用层级、满足条件后研究下一层。

### `guided-60m`

把同一策略延长到六十分钟，检查中期停滞和失控增长。

### `first-prestige`

持续运行固定策略，直到文明和大坍缩可用，或达到最长模拟时间。报告记录各层解锁和坍缩时间。

### `post-prestige-10m`

从第一轮结果执行大坍缩，使用固定恒定点分配，继续模拟十分钟。

## 报告指标

- 场景名和模拟时长。
- Git 提交、时间和场景版本。
- 各层首次解锁时间。
- 检查点资源数量和生产者数量。
- 研究点和研究速度。
- 各层产出、代谢和净变化。
- 合成次数。
- 大坍缩可用状态、恒定点收益和分配。
- 停滞、负净产出和失控增长警告。

JSON 是完整记录，Markdown 用于评审摘要。

## 验收规则

- 玩法或数值改动需要新报告。
- 检查点明显移动时记录原因。
- 场景停滞需要修复或明确写入设计目标。
- 界面显示速度与引擎不一致时先修正显示或逻辑。
- 新机制改变乘数时，模拟报告和玩家说明同时更新。

## 首轮审计发现

- 部分界面速度计算曾漏算引擎速度乘数，现已修正。
- “核聚变催化”里程碑曾缺少实际效果，现已接入原子合成成本。
- 生产注释曾沿用旧的自动合成描述，现已更新。
- 存档迁移能力仍然有限，未来状态结构变化需要明确版本处理。

## 架构原则

1. 数值模拟与界面、画布保持分离。
2. `js/constants.js` 继续作为调参来源。
3. 场景规则使用具名函数和明确条件。
4. 生成报告放入固定目录。
5. 评审通过的基线摘要进入版本库，探索报告保留本地。

## 开发流程

1. 记录机制会影响哪些数值和操作。
2. 运行当前基线。
3. 实现一个可评审范围。
4. 再次运行验证。
5. 对比报告并解释变化。
6. 理解差异后调整常量。
7. 一同提交机制、验证摘要和文档。

## 第一阶段范围

第一阶段只建立数值验证和修复已知一致性问题。大型玩法系统、视觉主题和框架迁移留给后续阶段。

## 已解决的实现选择

- 使用 Node `vm` 和最小 `window` 兼容层加载浏览器脚本。
- 临时报告放在 `reports/balance/` 并由 `.gitignore` 忽略。
- 评审基线放在 `docs/balance/reports/`。
- 第一轮大坍缩最长允许 24 个模拟小时。
- 第二轮使用固定恒定点分配进行比较。

当前协议见 `docs/balance/protocol.md`，后续工作见 `docs/product/roadmap.md`。
